# 1分ツール 週次Growth Research

原則として毎週月曜日、`automation/daily-site-operation.prompt.md` の日次実行に組み込んで1回実施する。別の公開処理や重複した日次実行を作らない。進行役は日次の事前確認と `site_analyst` による既存改善候補の整理を終えてから、次を行う。

1. **Growth Research**: `.codex/agents/site_growth_researcher.toml` の担当に `docs/roles/growth-researcher.md` に沿った調査を依頼する。直近28日と前の28日のSearch Consoleを同じ条件で比較し、Cloudflare、公開ページ一覧、利用できる公開検索結果を確認する。実測と仮説を分け、未対応の検索需要から最大3候補と見送り案を返してもらう。
2. **Strategist**: 日次の分析担当が出した既存改善候補とGrowth Researchの新規候補を、同じ利用者価値・需要根拠・実装負担・重複リスクで比較する。新規作成より既存改善の期待値が高ければ既存改善を選ぶ。根拠が弱ければ新規ツールを作らない。選択理由と完了条件を示す。
3. **Developer**: 進行役が採用案だけを実装する。新規ツールの実装は原則週1件まで。関連性が非常に高く同一機能基盤で安全に実装できる場合だけ、Strategistが理由を明示して複数ページを認める。
4. **Reviewer**: `site_reviewer` が根拠、差分、スマートフォンの使いやすさ、内部リンク、既存ページとの重複、検証結果を確認する。公開前に修正する指摘があれば実装へ戻して再レビューする。
5. **公開**: Reviewerが公開可とし、`npm.cmd run build` と `git diff --check`、変更した操作とリンクの確認が通った場合だけ、日次の公開手順に従う。

日次は既存価値の改善、週次は新しい検索需要の探索を担う。運用全体では既存改善を約70%、新規需要の探索と実験を約30%の目安とするが、件数や新規ページ数は目標にしない。薄いSEOページを大量生成せず、title・descriptionだけの変更を新規コンテンツと数えない。既存ページと利用価値がほぼ同じなら統合する。新ツールには内部リンクを用意する。

最終報告には、28日比較の条件、既存改善と新規候補の比較、採用・見送り理由、実装の有無、レビュー結果を短く残す。調査だけで終えた週もその判断を報告する。
