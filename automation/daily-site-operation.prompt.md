## 最初に行うこと

1. `AGENTS.md`、`docs/project-status.md`、`docs/site-operations.md`、`docs/roles/`内の日次4役のファイルを読む。月曜日は `automation/weekly-growth-research.prompt.md` と `docs/roles/growth-researcher.md` も読む。
2. `git status`、現在のブランチ、`origin/main`との差分を確認する。
3. 未コミットの変更がある場合は、ユーザーの作業を混ぜずに更新を中止し、状態だけ報告する。
4. 作業ツリーがきれいな場合だけ `git pull --ff-only` を実行する。
5. 当日にすでに意味のある更新コミットがある場合は、重複更新をせず、数値と公開状態を確認する。月曜日は週次Growth Researchも実施し、候補の評価まで行うが追加公開はしない。運用記録だけのコミットは「意味のある更新」に数えない。

## 4役の運用ループ

進行役が実装を担当し、プロジェクト設定 `.codex/agents/` の `site_analyst`、`site_strategist`、`site_reviewer` を順に起動して成果を受け渡す。各担当への依頼は対象と期待する出力を明示する。依存する作業は順に進め、レビュー前に公開しない。実行環境でサブエージェントが利用できない場合は同じ順序で役割ごとのメモを作り、最終報告に「独立レビュー未実施」と明記する。

1. **分析** (`docs/roles/analyst.md`): 取得元・期間・比較可能性・欠測と、改善候補の根拠を記録する。
2. **戦略** (`docs/roles/strategist.md`): 候補を評価し、変更0～3件または変更なしを決め、完了条件を示す。
3. **実装** (`docs/roles/developer.md`): 進行役が採用した範囲を変更・検証し、差分と結果を渡す。
4. **レビュー** (`docs/roles/reviewer.md`): 採用案、差分、計測解釈、検証を照合する。公開前に修正する指摘があれば実装へ戻し、再レビューする。

採用案、見送り理由、レビュー結果を最終報告に要約する。継続的な方針変更だけ `docs/decision-log.md` に記録する。

## 毎日の数値確認

利用できる場合は、ログイン済みブラウザを使って次を確認する。

- Google Search Console: `https://1mintool.com/` のクリック数、表示回数、CTR、平均掲載順位、上位クエリ、上位ページ
- Cloudflare Web Analytics: 1分ツールの直近24時間の訪問数、ページ閲覧数、主要ページ、Core Web Vitals

前回値と比較する。取得できない場合は推測や古い値の使い回しをせず、「取得不可」と理由を明記する。

毎週月曜日は、日次の分析担当が既存ページの直近28日と前の28日を比較した後、`automation/weekly-growth-research.prompt.md` を同じ実行の中で1回行う。Growth Research担当の新規候補を戦略担当へ渡し、既存改善候補と比較してから採用案を決める。月曜日以外は従来の4役だけで進める。

ページ数や更新回数そのものを成果にしない。検索語、対象ページ、変更理由を日次レポートに残す。

## 改善方針

数値とサイトの状態から、効果が高く安全な改善を0件から3件選ぶ。既存の文章ツール・例文・検索導線・スマートフォン操作・アクセシビリティ・表示速度を優先する。

更新するためだけの更新、日付だけの変更、検索向けの薄い大量ページ、SEOだけの更新履歴追加は行わない。十分な改善余地がない日は変更しなくてよい。

タイトル、説明文、見出しを直す場合は、検索語を不自然に繰り返さず、検索結果で内容と利用価値が一読で分かる文章にする。ゲームや1分コンテンツより、仕事の文章ツールと場面別例文を優先する。

## 実装と公開

1. 既存の設計と実装パターンに合わせて変更する。
2. `npm.cmd run build`、`git diff --check`、内部リンクと主要操作を確認する。
3. UIを変更した場合は、可能な範囲でPC幅とスマートフォン幅を確認する。
4. レビューで公開可となり、すべて成功した場合だけ、内容が分かるコミットを作成して `main` へpushする。
5. `https://1mintool.com/`、sitemap、旧Pages URLの転送を確認する。
6. コンテンツや機能を変更した場合だけ、実施内容を `docs/project-status.md` に記録する。数値確認だけの日は外部の日次レポートに記録し、記録だけを目的としたcommit・pushは行わない。

課金、広告契約、個人情報入力、認証情報や外部アカウント権限の変更、破壊的なGit操作は行わない。
